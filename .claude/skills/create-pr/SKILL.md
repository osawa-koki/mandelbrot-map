# PR 作成スキル

現在のブランチの変更内容を元にプルリクエストを作成する。`merge-pr` スキルで通過できる形に整えて作成する。

## 1. 現在の状態を確認する

```bash
git branch --show-current         # 現在のブランチ
git log main..HEAD --oneline      # main との差分コミット
git diff main --name-only         # 変更ファイル一覧
```

ブランチ名から Issue 番号を読み取る（フォーマット: `issues/番号_説明`）。Issue 番号が読み取れた場合は `gh issue view <番号>` で Issue の内容を確認し、タイトル・概要・ラベルの参考にする。

## 2. 親子構造かどうかを判断する

GitHub の sub-issue API で親子関係を確認する：

<!-- NOTE: gh CLI にはまだ sub-issue のネイティブサポートがないため、
     gh api 経由で REST API を呼び出している。
     gh CLI に対応コマンドが追加された場合はそちらに移行すること。
     参考: https://github.com/cli/cli/issues/10298 -->

```bash
# 親Issueかどうか（sub-issueが存在するか）
gh api repos/{owner}/{repo}/issues/{Issue番号}/sub_issues

# 子Issueかどうか（親Issueが存在するか）
gh api repos/{owner}/{repo}/issues/{Issue番号}/parent
```

- sub-issueが存在する → **親PR** を作成する
- 親Issueが存在する → **子PR** を作成する
- どちらでもない → 通常のPRを作成する

## 3. PR 情報を決定する

- **タイトル**: 変更内容を端的に表す（Issue タイトルをベースに調整）
- **ラベル**: Issue と同じラベルを使う（Issue がない場合は変更内容から推測）
- **ベースブランチ**:
  - 通常のPR・親PR → `main`（デフォルト）
  - 子PR → 親ブランチ（`--base 親ブランチ名` を指定する）
- **本文**: 以下のテンプレートを使う

```markdown
closes #番号

## テストカバレッジ

<!-- コードの変更・追加を含む場合は必ず記載する -->
| ファイル | Stmts | Branch | Funcs | Lines |
|---------|-------|--------|-------|-------|
| 変更したファイル | xx% | xx% | xx% | xx% |

## Checklist
- [ ] PRのタイトル・概要が実際の変更内容と一致している
- [ ] 対象IssueのスコープをPRが正しくカバーしている
- [ ] コーディング規約が守られている
- [ ] 変更・追加したコードにテストが存在し、カバレッジが十分である（低い場合はその理由を記載）
- [ ] コード変更に伴うドキュメントの最新化が必要な場合、対応済みである
```

テストカバレッジは、コードの変更・追加がある場合のみ記載する。スキルファイル・設定ファイル・ドキュメントのみの変更であれば省略してよい（その旨をコメントで明記する）。

チェックリストの各項目は、作成時点で自己チェックして `[x]` にしておく。未確認の項目は `[ ]` のまま残してユーザーに判断を委ねる。

**親PRの場合の追加事項：**
- 親PRは子PRが全てマージされるまでマージしない旨を記載する
- sub-issue の一覧を本文に含めると見通しが良くなる

## 4. ブランチをプッシュして PR を作成する

リモートにブランチが存在しない場合は先にプッシュする：

```bash
git push -u origin <ブランチ名>
```

PR を作成する：

```bash
# 通常のPR・親PR
gh pr create --title "タイトル" --body "本文" --label "ラベル" --assignee "@me"

# 子PR（親ブランチをベースに指定）
gh pr create --title "タイトル" --body "本文" --label "ラベル" --assignee "@me" --base <親ブランチ名>
```

担当者は `@me` を設定する。開発ワークフローの規約により、IssueとPRには必ず担当者を設定する必要があるため。

## 5. 結果を報告する

作成した PR の URL をユーザーに伝える。

- 通常のPR → `merge-pr` スキルでマージできることを案内する
- 子PR → 親ブランチへのマージであることを明示する
- 親PR → 子PRが全てマージされた後にマージすることを案内する


## エラー時の自己修正

このスキルの実行中にエラーや不具合が発生した場合：

1. ユーザーにエラー内容と原因を報告する
2. エラーの根本原因がスキルの記述（手順の誤り、コマンドの間違い、考慮漏れなど）にある場合は、このSKILL.mdを修正して再発を防止する
3. 修正内容をコミットに含める
