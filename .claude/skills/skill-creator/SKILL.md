# Skill Creator

`.claude/skills/` に新しいSkillを作成する、またはすでに存在するSkillを改善・更新・修正する。

## プロセス

作成・更新は **参考資料確認 → 公式ドキュメント確認 → 意図の把握 → ドラフト作成 → テスト → 改善** のサイクルで行う。

### 1. Anthropics公式skill-creatorを参照する

スキルを作成・改善するたびに、必ず最初にAnthropics公式のskill-creatorを取得してベストプラクティスを確認する。

```
WebFetch: https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md
```

公式skill-creatorには、スキルの設計思想・テスト手法・description最適化・改善ループなどの最新ベストプラクティスが含まれる。内容が更新されている可能性があるため、都度取得して確認する。

### 2. 公式ドキュメントを確認する

スキルを作成・改善するたびに、必ず公式ドキュメントも取得して最新の仕様を確認する。

```
WebFetch: https://code.claude.com/docs/ja/skills
```

フロントマターのフィールド、引数変数、高度なパターン（動的コンテキスト注入・サブエージェント実行）などの仕様は変わる可能性があるため、都度ドキュメントから確認することで常に正しい情報をもとに実装できる。

### 3. 意図を把握する

作業を始める前に以下を明確にする。不明な点はユーザーに確認する。

- このSkillは何をするか？
- いつトリガーされるべきか（ユーザーがどう言ったとき）？
- どんな入力を受け取り、何を出力するか？
- `$ARGUMENTS` で引数を受け取るか？
- ユーザーが呼び出すか、Claudeが自動で呼び出すか、またはその両方か？
- サブエージェントで分離して実行する必要があるか？

### 4. SKILL.md を書く

`.claude/skills/<name>/SKILL.md` を作成する。ファイル名はディレクトリ名と一致させる。

**フロントマターのフィールド（公式ドキュメントで確認した最新情報をもとに設定する）：**

```yaml
---
name: skill-name                  # 省略可。省略時はディレクトリ名を使用。小文字・数字・ハイフンのみ（最大64文字）
description: "..."                # 推奨。トリガー精度を左右する最重要フィールド
argument-hint: "[args]"           # 省略可。オートコンプリートに表示されるヒント
user-invocable: true              # 省略可。false にするとメニューに非表示（Claudeのみ呼び出し可）
disable-model-invocation: false   # 省略可。true にするとClaudeが自動起動しない（ユーザーのみ呼び出し可）
allowed-tools: Read, Grep         # 省略可。スキルがアクティブな場合にClaudeが使用できるツール
model: "..."                      # 省略可。スキルがアクティブな場合に使用するモデル
context: fork                     # 省略可。fork にするとサブエージェントコンテキストで実行
agent: Explore                    # 省略可。context: fork 時のサブエージェントタイプ
---
```

**引数変数（`$ARGUMENTS` の他に以下も使用できる）：**

| 変数 | 説明 |
|------|------|
| `$ARGUMENTS` | スキル呼び出し時に渡された全引数 |
| `$ARGUMENTS[N]` / `$N` | N番目の引数（0始まり）。例: `$0` で最初の引数 |
| `${CLAUDE_SESSION_ID}` | 現在のセッションID |
| `${CLAUDE_SKILL_DIR}` | このSKILL.mdを含むディレクトリのパス（バンドルされたスクリプト参照に使用） |

**descriptionを書く際のポイント：**
アンダートリガー（必要なのに起動しない）を防ぐため、ユーザーが自然に使うキーワードを具体的に含める。「〜のときに使用する」という表現で明示的にトリガー条件を示す。

**本文を書く際のポイント：**
- 命令形で書く（「〜する」「〜せよ」）
- 理由を添える（なぜそうするかを説明することで、Claudeがエッジケースでも正しく判断できる）
- `ALWAYS/NEVER` は避け、代わりに理由で動機付ける
- 500行以内に収める（詳細なリファレンスは別ファイルに分離する）
- ルールや手順に特定のディレクトリ名・クラス名・ファイル名などの具体的な値を書かない。Skillはプロジェクト内の全ての場所で共通して利用されるため、特定の実装に依存した記述は誤動作の原因になる。具体的な値は例示（コードブロックや「例：」の形）としてのみ使う
- 本文の末尾に「エラー時の自己修正」セクションを含める（後述）

**呼び出し制御の選択指針：**

| 用途 | 設定 |
|------|------|
| ユーザーが手動で呼び出す（デプロイ・コミットなど副作用のあるワークフロー） | `disable-model-invocation: true` |
| Claudeが自動で使う背景知識（ユーザーが直接呼び出す意味がないもの） | `user-invocable: false` |
| 両方から呼び出せる（デフォルト） | 設定不要 |

**「エラー時の自己修正」セクション：**

全スキルに以下のセクションを含める。スキル実行中にエラーや不具合が発生した場合、同じ問題が繰り返されないようスキルファイル自体を修正する仕組みを入れるため。

```markdown
## エラー時の自己修正

このスキルの実行中にエラーや不具合が発生した場合：

1. ユーザーにエラー内容と原因を報告する
2. エラーの根本原因がスキルの記述（手順の誤り、コマンドの間違い、考慮漏れなど）にある場合は、このSKILL.mdを修正して再発を防止する
3. 修正内容をコミットに含める
```

### 5. テストする

Skill作成後、実際のユーザー入力を想定した2〜3のプロンプトで動作を確認する。

確認すること：
- 期待通りのトリガーで起動するか
- 出力が正しいか
- エッジケースで適切に動作するか

### 6. 改善する

テスト結果に基づいて改善する。

- フィードバックを一般化する（特定のケースに過学習させない）
- プロンプトはできるだけ簡潔に保つ
- descriptionを調整してトリガー精度を高める

### 7. CLAUDE.md の重複を削除する

スキルが定義した内容と同じことが `CLAUDE.md` に書かれていれば削除し、スキルへの参照（「`スキル名` スキルを参照すること。」）に置き換える。スキルが正式な定義場所となるため、CLAUDE.md への重複はメンテナンスコストを増やすだけになる。

このステップはコミットの前に必ず実施する。

## ディレクトリ構成

シンプルなSkillは `SKILL.md` 1ファイルで十分。複雑な場合はサブディレクトリを使う：

```
.claude/skills/<name>/
├── SKILL.md          # 必須
├── references/       # 詳細なリファレンス（必要なら）
└── scripts/          # 再利用可能なスクリプト（必要なら）
```

## 完了条件

- `SKILL.md` が `.claude/skills/<name>/` に作成されている
- フロントマターの `name` がディレクトリ名と一致している（または省略してディレクトリ名を使用）
- 「エラー時の自己修正」セクションが含まれている
- 動作テストを実施し、期待通りに動くことを確認している
- CLAUDE.md の重複削除が完了している（ステップ7を実施済み）
- コミットしている

## エラー時の自己修正

1. ユーザーにエラー内容と原因を報告する

3. 修正内容をコミットに含める
